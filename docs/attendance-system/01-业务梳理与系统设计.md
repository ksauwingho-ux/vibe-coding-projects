## 〇、前提校准：我们到底在做什么

v4.0 的自我定位是"已交付、待验收的业务基线"，但**本仓库不含 attendance-system 任何代码**。因此实际处境需要先说清：

| 表面理解 | 实际处境 |
|---|---|
| 这是一份待实现的新需求 | 不是。它是一份被真实数据校验过的成熟规格 |
| 这是一份要改的存量系统文档 | 不是。代码不在手上 |
| **真实处境** | **拿一份高质量规格 + 一套可断言的验收基线，重建一套系统** |

这个定位带来三个直接结论，决定了后面所有安排：

1. **需求阶段可以压缩到接近零。** 规格已到字段级，不需要再做需求调研。省下的时间应全部投入"判定引擎正确性"和"一致性保障"。
2. **我们拿到了极其罕见的东西——可断言的验收目标。** 31,792 行真实数据必须判出 `正常 15,442 / 旷课 14,185 / 待处理 2,001 / 迟到 164`。这不是"用户觉得好用"这种软验收，而是一行代码写错就会红的回归断言。**这个断言必须是第一个里程碑，不是最后一个。**
3. **v4.0 自己记录了一次失败的技术路线切换**（React + Vite + TS + Nitro + 云库 + 多维表格 → FastAPI + SQLAlchemy + Jinja2 + SQLite）。这次重建的第一个决策点就是：不要重复走一遍那条已经被证伪的路（见 §6 · D0）。

关于"智能"二字：这套系统的智能不在 AI，而在**把辅导员人工清洗 Excel 的判定过程规则化、可追溯化**——历史上仅"只认刷脸"这一条口径错误就造成 8,314 行误判。先把确定性规则做对，AI 增强留二期（见 §6 · D8）。

## 一、系统目标

### 1.1 现状的四个断点

| # | 断点 | 具体表现 | 谁在受苦 |
|---|---|---|---|
| 1 | 数据不落地 | 导出的 Excel 散落在个人电脑，无统一台账 | 学院层面无法汇总监管 |
| 2 | 判定口径不透明 | 学校系统只给「考勤结果 + 考勤方式」，是否算缺勤要人工清洗，各辅导员口径不一 | 辅导员重复劳动 + 学生感到不公 |
| 3 | 申诉靠线下 | 学生有异议要当面找老师，无留痕、无时限、无进度 | 学生 + 辅导员双向消耗 |
| 4 | 请假与考勤脱节 | 请假在另一套表，审批通过后考勤不自动更正，仍显示旷课 | 学生被误记旷课 |

四个断点的共性：**同一个事实（某人某节课到没到）散落在三套互不通信的载体里**（学校导出表、个人电脑、请假表）。系统的本质是把这个事实收敛成一张唯一台账，再围绕它建流程。

### 1.2 目标定义

> 建成一套自建 Web 应用，把「导入 → 判定 → 申诉 → 审批 → 公示 → 锁定」全链条线上化，并与请假审批打通。

四个可度量目标：

| 目标 | 度量方式 | 目标值 |
|---|---|---|
| 判定口径统一 | 真实数据判定分布回归 | 100% 复现 §4.3 基准分布 |
| 过程全程留痕 | 写操作审计覆盖率 | 100%（申诉/请假/核对/改判/任命，无例外） |
| 结果可追溯 | 每条考勤可追到判定依据条文 | `judge_reason` 字段非空率 100% |
| 学生自助 | 学生无需线下即可查看进度 | 申诉全流程线上，含申诉公示倒计时 |
| **学生每日知晓** | 学生当天即知道本人考勤结果 | 每日定时推送覆盖率 ≥ 已绑定学生的 99% |

### 1.3 价值分层（汇报视角）

| 对象 | 拿到什么 |
|---|---|
| 学生 | **每天收到自己的考勤告知**，当天就知道有没有被记旷课；有异议有地方说、进度自己查，不用堵办公室门口 |
| 副班长 / 学生干部 | 明确的职责与工具（待处理核对、申诉一审二审），学生自治真正落地而不是口号 |
| 辅导员 | 从"每周手工清洗几千行 Excel"变成"看看板 + 审批例外"，2,432 人的监管从不可能变为日常 |
| 学院 | 一张全院统一台账 + 完整审计链，考勤数据首次可用于评优、预警、教学质量分析 |

## 二、参与角色

### 2.1 角色定义

| 角色 | 代码 | 核心职责 | 数量 |
|---|---|---|---|
| 学生 | `student` | 查看本人考勤、提交申诉、请假申请 | 2,430 |
| 副班长 | `monitor` | 本班考勤、**待处理核对**、**申诉一审**、请假进度只读 | **0（待任命）** |
| 学生干部 | `student_cadre` | **申诉二审（终审）**、发起公假 | **0（待任命）** |
| 辅导员 | `counselor` | 最高权限：导入、改判、看板、推送、任命、审批、代审 | 2 |

角色由辅导员在 `/counselor/roles` 设置，可指派范围仅 `student / monitor / student_cadre`；辅导员角色不在该页调整范围内；每次变更写审计日志。

> ⚠️ **上线阻塞项 A · 干部任命**：实测 `students.role` 分布为 `counselor 2 / student 2430`，副班长与学生干部**均为 0 人**。这意味着申诉一审二审无归属人，流程只能靠辅导员代审兜底跑通，"学生自治审核"的设计目的完全落空。这是组织问题不是技术问题，需要用户提供名单，**必须 Day 1 就发起，不能等开发完再说**（见开发计划 §3）。

> ⚠️ **上线阻塞项 B · 学生 WPS 推送地址覆盖率**（D4 改判后新增）：每日考勤告知进入一期后，能不能推到学生，取决于 `students.wps_user_id` 有多少人是填好的。**这个数字目前未知，必须先测出来。** 若覆盖率低，这个一期核心功能等于不存在。
>
> 关键区分（文档 §8.2 已强调，此处是它的业务后果）：`wps_user_id`（推送地址）与 `is_bound`（登录绑定）是两回事。**推送地址理论上可从 WPS 企业组织架构批量回填，不需要 2,432 名学生每人手动操作一次**——若可行，这个阻塞项就从"组织推广问题"降级为"一次性脚本"。**这是 D4 改判后第一件要验证的事**，因为两种情况的提前期差了几个数量级。

### 2.2 角色叠加（重要设计约定）

副班长与学生干部**首先是学生**。登录后同时拥有两套功能，导航栏同时展示两类入口，不需要切换账号：

- 学生端：我的考勤 / 提交申诉 / 申诉进度 / 请假申请 / 我的请假
- 管理端：一审或二审待办 / 本班考勤 / 待处理核对 / 发起公假

**存储上 `students.role` 单值即可**，管理权限由角色值推导，无需多值字段。这是一个容易做复杂的地方——不要引入 role 数组或 RBAC 表。

### 2.3 权限矩阵

| 功能 | 学生 | 副班长 | 学生干部 | 辅导员 |
|---|:-:|:-:|:-:|:-:|
| 查看本人考勤 | ✓ | ✓ | ✓ | ✓ |
| 查看本班考勤 | — | ✓ | ✓ | ✓ |
| 查看全院考勤 | — | — | — | ✓ |
| 提交申诉 | ✓ | ✓ | ✓ | ✓ 代提 |
| 提交请假 | ✓ | ✓ | ✓ | ✓ 代办 |
| 发起公假（多人同行） | — | — | ✓ | ✓ |
| 请假审批（通过/驳回） | — | — | — | ✓ |
| 请假进度只读旁观 | — | ✓ 本班 | ✓ 本班 | ✓ |
| 待处理考勤核对 | — | ✓ 本班 | ✓ 本班 | ✓ |
| 申诉一审 | — | ✓ 本班 | — | ✓ 代审 |
| 申诉二审（终审） | — | — | ✓ | ✓ 代审 |
| 修改任意考勤数据 | — | — | — | ✓ |
| 数据导入 / 重建统计 | — | — | — | ✓ |
| 每日推送 | — | — | — | ✓ |
| 干部任命管理 | — | — | — | ✓ |

### 2.4 防自审规则（硬约束，不可放开）

| 场景 | 处理方式 |
|---|---|
| 申诉人是**副班长本人** | 跳过一审，直接进辅导员代审队列（`bypass_first`） |
| 申诉人是**学生干部本人** | 二审不进本人待办，由其他干部审；**该班唯一干部时由辅导员代审兜底** |
| 请假审批 | 审批人固定为辅导员，天然无自审问题 |

> **辅导员兜底入口必须存在。** 某班只有 1 名干部是真实存在的高风险场景，缺少兜底会导致该生申诉**永久卡死**。

### 2.5 权限实施原则

因为是自建 UI，所有数据可见性约束**必须在应用层实现**，不能依赖任何平台权限体系：

- 学生端所有查询强制带 `student_no = 当前绑定学号`
- 副班长 / 干部查询强制带 `class_name = 本人班级`
- 辅导员查询无班级约束
- **前端隐藏按钮 ≠ 权限控制，服务端必须同步校验**

## 三、业务流程

### 3.0 全局流程地图

```
                    ┌─────────────────────────────────────┐
  学校考勤系统       │         链 A：数据入库与判定          │
  导出 Excel  ──────▶│  解析→去重→学号映射→请假匹配→判定    │
  (11 列)           │  →分批写入→名册补建→重建统计→批次审计 │
                    └──────────────┬──────────────────────┘
                                   │  attendance.final_judgment
                    ┌──────────────┴──────────────┬─────────────────┐
                    ▼                             ▼                 ▼
         ┌──────────────────┐       ┌──────────────────┐   ┌──────────────┐
         │  链 B：申诉闭环   │       │  链 D：待处理核对 │   │ 链 E：手动改判│
         │  学生发起         │       │  副班长核实       │   │ 辅导员直接改  │
         │  副班长一审       │       │  到场/缺勤+备注   │   │ +备注+审计    │
         │  干部二审(终审)   │       └────────┬─────────┘   └──────┬───────┘
         │  公示 7 天→锁定   │                │                    │
         └────────┬─────────┘                │                    │
                  │                          │                    │
         ┌────────┴──────────────────────────┴────────────────────┴───────┐
         │   统一副作用：改判 attendance + 增量维护 class_daily_stat        │
         │             + 写 audit_log + 发 notification                    │
         └─────────────────────────────────────────────────────────────────┘
                                   ▲
         ┌─────────────────────────┴───────────────────────────┐
         │  链 C：请假闭环（并行链，唯一能"批量"改判的流程）      │
         │  发起→辅导员审批→通过则四重匹配写回考勤「请假」        │
         │  →撤销申请→辅导员确认→回滚并完整重判                  │
         └─────────────────────────────────────────────────────┘
```

**关键认知**：五条链（A/B/C/D/E）最终都汇聚到同一组副作用上。**把这组副作用做成唯一的、被强制复用的服务层函数，是整个系统工程质量的分水岭**（见 §3.6、§4.4）。

### 3.1 链 A：数据入库与判定（9 步）

| 步 | 动作 | 关键约束 |
|---|---|---|
| 1 | 解析 | 11 列同构解析，排除表头；**按列名定位，不按列序、不按文件名** |
| 2 | 日期段去重 | 取批次日期范围 → 拉已存在记录 → 按**业务唯一键**比对，命中跳过 |
| 3 | 学号映射 | 按「姓名 + 班级」回填学号（实测覆盖率 99.74%） |
| 4 | 请假匹配 | 查系统内已通过请假单，按**四重条件**覆盖 |
| 5 | 判定 | 走 §4.2 规则 |
| 6 | 分批写入 | **500 条/批**，显示进度与失败定位 |
| 7 | 名册补建 | 考勤有而名册无的学生 → 自动补建（学号空字符串，`origin=auto`） |
| 8 | 重建统计 | 对该日期段**全量重建** `class_daily_stat`（幂等：先按日期删旧再重算） |
| 9 | 记录批次 | 写 `sync_batch` 审计 |

失败处理：批量写入失败必须报出**第几条起失败**；空值统一转空字符串；导入中断可重复导入（去重保证幂等）。

> **解耦要求**：导入层与判定引擎必须解耦，接口约束为「输入 11 列结构化行 → 输出判定结果」。未来对接学校考勤 API 时只替换数据来源，判定 / 统计 / 推送全部复用。这不是可选优化，是明确的架构要求。

### 3.2 链 B：申诉闭环（状态机）

**两个正交维度**——这是"这单怎么了"与"下一步该谁动"分开的关键设计：

- `status`（处境）：`pending / approved / rejected / locked / withdrawn`
- `stage`（下一步该谁）：`first / second / counselor / done`

```
  待一审 ──一审通过──▶ 待二审 ──终审通过──▶ 成立(公示中) ──公示期满──▶ 已锁定
 (pending  │           (pending  │          (approved              (locked
  /first)  │            /second) │           /done)                 /done)
           │                     │
       一审驳回               终审驳回
           ▼                     ▼
        已驳回 (rejected/done)  已驳回
```

对外展示状态在 `approved` 上**再叠加时间状态**，区分「申诉成立（公示中）」与「申诉成立（已锁定）」。

**时限规则**：

| 规则 | 计算方式 | 超时行为 |
|---|---|---|
| 一审审核时限 | 申诉提交时间 + 7 天 | 按钮禁用 + 提示「已超时，转辅导员代审」 |
| **申诉公示期** | 终审时间 + 7 天 | 期满锁定，申诉入口关闭 |

> ⚠️ **两个"公示"必须分开，不要混用**：
> - **申诉公示期**（本表）= 申诉成立后挂 7 天再锁定，是**申诉流程内部的一个阶段**
> - **每日考勤公示 / 告知**（§6 推送）= 每天把本人考勤推给学生看、自己核对，是**独立的日常推送功能**
>
> 两者受众、触发、周期完全不同。文档中凡提"公示期"一律指前者，提"每日告知"一律指后者。

- **超时处理由服务端兜底**，前端按钮禁用只是提示，避免绕过前端提交
- 辅导员代审不受时限限制
- 每日巡检自动把超时单转辅导员（`POST /counselor/appeals/sweep`），避免卡死

**申诉范围**：

- 可申诉：**旷课、迟到、早退**（D2 已拍板，按 v3 从宽）
- 不可申诉：待处理（走链 D 核对，不进申诉）
- 学生只能请求改判为「正常」（请假走请假子系统，不从申诉绕）
- 同一考勤记录**同时只能有一张进行中**的申诉单；驳回/撤回后允许补充佐证重新申诉
- 已锁定记录不可再申诉

### 3.3 链 C：请假闭环（状态机）

```
  发起（学生本人 / 干部代办 / 辅导员代办）
    │  公假可勾选多名同行学生，一张单覆盖多人
    ▼
  pending ──辅导员通过──▶ approved ──▶ 按四重条件匹配考勤，命中的改判「请假」
    │                        │
  驳回(必填理由)          学生申请撤销
    ▼                        ▼
  rejected            approved + revoke_requested_at 非空
                      ＝「撤销待确认」（**此期间请假仍然生效**）
                             │
                        辅导员确认
                             ▼
                        revoked ──▶ 考勤回滚 + 完整重判
```

> 「撤销待确认」**不是独立 status 值**，而是 `status=approved` 且 `revoke_requested_at` 非空 且 `revoke_confirmed_at` 为空。这是个容易实现错的点：不要加新枚举值。

**请假类型与佐证**：

| 类型 | 佐证 | 特殊性 |
|---|---|---|
| 公假 | 选传 | **可勾选多名同行学生**，一张单覆盖多人 |
| 病假 | **必须上传** | 图片上传 + 预览 |
| 事假 / 其他 | 选传 | — |

**四重匹配条件**：`姓名 + 班级名称 + 日期 + 节次` 全部命中：

| 请假方式 | `periods` 取值 | 覆盖范围 |
|---|---|---|
| 按天请假 | 空 | 当天**全部**课程 |
| 按节次请假 | 如 `1,3,5` | 只覆盖指定节次（1–12） |

- 多张公假覆盖同一学生同一时段 → **并集生效**，不冲突不报错
- 只认系统内审批通过的请假单（历史 9 条外部数据丢弃不导入）
- **覆盖只作用于「旷课」**；正常 / 迟到 / 早退不受请假影响

**过程可见性**：副班长对本班请假单**只读旁观**，可看进度与日志，不能通过/驳回。请假日志记录每一步：发起 / 审批 / 驳回 / 撤销申请 / 撤销确认。

### 3.4 链 D：待处理核对（副班长职责）

「正常 + 方式为空」的 **2,001 行**进入待处理池：

| 核实结论 | 改判为 |
|---|---|
| 到场 | 正常 |
| 缺勤 | 旷课 |

- **必须填备注**（留痕强制）
- 改判后同步更新统计 + 写审核日志 + 通知学生
- 支持按班级筛选；**2,001 条是实际工作量，页面必须能按班分批处理而不是一屏全渲染**

### 3.5 链 E：辅导员手动改判

筛选（班级/判定/日期/姓名模糊）→ 修改判定 + 备注 → **必须写审计日志**（`action=override`）→ 置位 `lock_judgment`。

### 3.6 改判路径汇总表（★ 开发时的核心检查表）

**五条路径都必须完成同一组四件事，一件都不能漏：**

| # | 改判路径 | 触发者 | 改 `attendance` | 维护 `class_daily_stat` | 写 `audit_log` | 发 `notification` | 置 `lock_judgment` |
|---|---|---|:-:|:-:|:-:|:-:|:-:|
| 1 | 申诉终审通过 | 干部/辅导员 | ✓ | 增量 ±1 | `final_approve` | ✓ | **✓** |
| 2 | 待处理核对 | 副班长 | ✓ | 增量 ±1 | `pending_review` | ✓ | **✓** |
| 3 | 辅导员手动改判 | 辅导员 | ✓ | 增量 ±1 | `override` | ✓ | **✓** |
| 4 | 请假审批通过 | 辅导员 | ✓ 批量 | 增量 ±1 逐条 | `leave` 流水 | ✓ | ✗ |
| 5 | 请假撤销确认 | 辅导员 | ✓ 回滚重判 | 增量 ±1 逐条 | `leave` 流水 | ✓ | ✗（**但必须尊重已置位的行**） |
| 6 | 导入 | 辅导员 | ✓ 批量 | **整段重建** | `sync_batch` | ✗ | ✗ |

**路径 5 是全系统最容易出错的地方**：请假撤销后要"完整重判"，但**不能覆盖人工结论**。`lock_judgment=1` 的行必须跳过。漏掉这个判断，副班长核对过的 2,001 条会被一次撤销操作静默冲掉。

## 四、判定引擎（系统心脏）

### 4.1 输入形态

学校导出明细**没有学号字段**，必须以「姓名 + 班级名称」关联名册。固定 11 列：

```
姓名 | 班级名称 | 课程名称 | 上课老师 | 课程节次 | 教室位置 | 周次 | 签到时间 | 考勤结果 | 生成日期 | 考勤方式
```

### 4.2 判定规则（完整）

```
有效方式 = { 刷脸, istudy, 二维码 }      无效方式 = { 刷卡 }      空方式 = ""

若 考勤结果 == 正常:
    方式 ∈ 有效方式      → 正常
    方式 == 刷卡         → 旷课
    方式 == ""           → 待处理        （模糊态，交副班长核实）
    其它未知方式         → 待处理        （D1 已拍板：保持防御性设计）

若 考勤结果 == 迟到 或 早退:
    → 原样保留（迟到 / 早退）

若 考勤结果 == 旷课:
    查系统内【已审批通过】的请假，按「姓名+班级+日期+节次」四重匹配
        命中 → 请假        未命中 → 旷课

未识别的考勤结果  → 待处理
```

**为什么刷卡算旷课**：刷卡可由他人代刷，学校视为不可信签到。这是规则中最容易引起学生异议的一条，**申诉入口必须畅通**。

**历史误区（已纠正，务必不要走回去）**：早期只认「刷脸」有效，导致 istudy（4,043 行）与二维码（4,271 行）被误判为缺勤，共 **8,314 行误判**。三者都算正常签到。

**设计原则「数据面前不猜」**：规则没覆盖的组合降级为「待处理」交人工核实，而不是猜一个结论。

### 4.3 输入组合穷举与验收基准

实测 31,792 行共 10 种组合，**无未知方式**：

| 考勤结果 | 考勤方式 | 行数 | 判定 |
|---|---|---:|---|
| 正常 | 刷卡 | 9,164 | 旷课 |
| 正常 | 刷脸 | 7,128 | 正常 |
| 旷课 | （空） | 5,021 | 旷课（或被请假覆盖） |
| 正常 | 二维码 | 4,271 | 正常 |
| 正常 | istudy | 4,043 | 正常 |
| 正常 | （空） | 2,001 | 待处理 |
| 迟到 | istudy | 105 | 迟到 |
| 迟到 | 刷卡 | 24 | 迟到 |
| 迟到 | 刷脸 | 23 | 迟到 |
| 迟到 | 二维码 | 12 | 迟到 |

**验收基准分布（硬指标，改版后必须复现）**：

| 最终判定 | 行数 | 占比 | 加总校验 |
|---|---:|---:|---|
| 正常 | 15,442 | 48.6% | 7,128 + 4,271 + 4,043 ✓ |
| 旷课 | 14,185 | 44.6% | 9,164 + 5,021 ✓ |
| 待处理 | 2,001 | 6.3% | 2,001 ✓ |
| 迟到 | 164 | 0.5% | 105 + 24 + 23 + 12 ✓ |
| **合计** | **31,792** | 100% | ✓ |

> 📌 **一个值得注意的发现**：穷举表 10 种组合中**没有任何「早退」行**，验收分布里也没有早退。也就是说实测 31,792 行中**早退为 0 条**。正因为如此，D2 最终定为"早退可申诉"——当下零成本（不增加任何审核负担），却永久消除了将来出现早退数据时学生无处申诉的争议。

### 4.4 三条不可动摇的技术铁律

**铁律 1 · 判定纯函数化**
判定逻辑必须是不依赖数据库会话的纯函数：`(raw_result, raw_way, 已通过请假集) → (final_judgment, judge_reason)`。理由：这是唯一能让 31,792 行回归测试跑得快、跑得稳的形态；也是 §3.1 导入层解耦要求的前提。

**铁律 2 · 一致性铁律**
`class_daily_stat` 的总和**恒等于** `attendance` 表的实际内容。§3.6 所有路径必须同步维护统计。落地手段：所有改判**只允许**走同一个服务层函数（例如 `apply_judgment_change()`），由它统一负责改表 + 增量统计 + 审计 + 通知。**禁止任何地方直接 UPDATE attendance 的 final_judgment。** 建议加一条断言型测试：随机改判 N 次后，`sum(class_daily_stat.cnt) == count(attendance)` 且分组分布一致。

**铁律 3 · 人工结论锁（`lock_judgment`）**
待处理核对 / 辅导员手动改判 / 申诉终审生效三种情况置位 `lock_judgment=1`，防止后续批量重判静默覆盖人工结论。这是文档中"隐藏但关键"的设计，**也是最容易在重建时漏掉的一个字段**。

## 五、数据需求

### 5.1 权威数据源（唯一，不可替换）

| 文件 | 用途 | 规模 |
|---|---|---|
| `历史考勤信息 (8).xlsx` | 考勤原始数据，唯一权威 | 31,792 × 11 |

> ⚠️ **名册必须用 (27)**。用 `(4)`（832 人、仅 26 级）会导致 **95.2%** 的考勤行匹配不到学号，进而推送、聚合、看板全部失效。源目录：`C:\Users\user\Desktop\26年考勤系统搭建\`

### 5.2 数据分层

| 层 | 表 | 特征 |
|---|---|---|
| **主数据** | `students` | 人的唯一真相，含角色与 WPS 绑定 |
| **事实表** | `attendance` | 主事实，一行 = 一人一节课一次考勤，60 万+/学期 |
| **派生表** | `class_daily_stat` | 预聚合，**可从事实表完全重算**，看板专用 |
| **流程表** | `appeal`、`leave_request`、`leave_student` | 承载状态机 |
| **审计/旁路** | `audit_log`、`notification`、`sync_batch` | 只增不改 |

分层的意义：**派生表可重建、审计表只增不改、流程表有状态机**——三类表的测试策略完全不同（派生表测一致性、审计表测覆盖率、流程表测状态迁移）。

### 5.3 表清单

| 表 | 用途 | 量级 |
|---|---|---|
| `students` | 学生名册 + 角色 + WPS 绑定 | 2,432 |
| `attendance` | 考勤明细（主事实表） | 31,792/周；60 万+/学期 |
| `class_daily_stat` | 班级日预聚合（看板专用） | 884/周；约 2.4 万/学期 |

| `leave_request` | 请假单 | 千级/学期 |

### 5.4 关键键与约束（★ 建表时逐条对照）

| 表 | 键/约束 | 说明 |
|---|---|---|
| `students` | 唯一键 `(name, class_name)` | `student_no` **可为空字符串**（考勤补建的老生） |
| `attendance` | 业务唯一键 `name + class_name + course_name + period + att_date` | 导入去重依据，已用 31,792 行真实数据验证**全表唯一** |
| `leave_student` | 唯一键 `(leave_no, name, class_name)` | 公假多人，一行一人 |
| `appeal` | **刻意不加唯一约束** | "进行中唯一"由**业务层**保证；加唯一约束会堵死"驳回后补充佐证重新申诉" |
| `class_daily_stat` | `att_date + class_name + judgment + cnt` | 导入后整段重建（幂等），单条改判增量 ±1 |

**`students` 上两个容易混淆的字段**：

- `wps_user_id` = IM 推送地址
- `is_bound` = 登录绑定完成标记

**这是两个不同的东西。批量回填脚本只动前者，不得影响登录绑定关系。**

**`attendance` 的关键字段**：

```
raw_result       原始：正常 / 迟到 / 早退 / 旷课
raw_way          原始：刷卡 / 刷脸 / 二维码 / istudy / 空
final_judgment   最终：正常 / 迟到 / 早退 / 请假 / 旷课 / 待处理
judge_reason     判定依据（可追溯到规则条文）
is_leave         是否被请假覆盖
lock_judgment    人工结论锁（见铁律 3）
is_overridden / override_by / pending_note / reviewed_by    人工复核留痕
batch_id / appeal_id / appeal_status                        关联与冗余
```

这几条 v4.0 没有明确规定，但会在开发中真实撞上，建议在动手前补定义：

| # | 问题 | 风险 | 建议 |
|---|---|---|---|
| 1 | **学期边界**：`att_date` 跨学期如何隔离？ | 60 万+/学期累积后，看板与统计的默认范围含义不清；学号可能跨学期变化 | 加 `semester` 字段或统一按日期范围过滤，看板默认"当前学期" |

| **R10** | **每日 2,432 条推送的量级风险** | 分片错误 → 部分学生静默收不到；平台限流 → 推送拖长甚至中断 | 25 片逐片计数；失败落库可重推；先在小班级灰度一天再全量 |
| **R11** | **导入源可能存在重复行**（2026-09-19 截图发现，待核实） | 若业务唯一键并非全表唯一，去重会**静默删掉真实记录** | 见 §5.6；导入时把"因去重跳过"的行留档到 `sync_batch`，可随时倒查 |
