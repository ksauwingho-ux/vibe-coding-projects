## 〇、计划原则

**不按页面分期，按"可验证的价值闭环"分期。**

24 个页面按页面切会得到一堆半成品：页面能打开但数据是错的。按闭环切，每个里程碑结束时都有一个**能用真实数据断言的结果**。

三条排期原则：

1. **判定引擎第一。** 它错了后面全白做，而且它的验收指标是全项目最硬的（31,792 行 → 精确到个位的分布）。好消息：基准分布 §3.5 本身就是"无请假记录参与"时的值，所以 M1 **不依赖请假子系统**，可以完全独立开工。
2. **改判底座在最简单的场景里建立，之后强制复用。** 五条改判路径共用同一组副作用（改表 + 增量统计 + 审计 + 通知）。把它做成唯一入口 `apply_judgment_change()`，在最简单的"待处理核对"里首次落地并测通，再给申诉和请假复用。**不要让申诉和请假各写一遍。**
3. **最难的放最后但不放弃。** 请假撤销回滚 + 完整重判 + 尊重 `lock_judgment` 是全系统最容易出脏数据的路径，必须在统计维护与判定引擎都已稳定后再做。

## 二、里程碑详情

**产出**

- 项目骨架：FastAPI + SQLAlchemy + Jinja2，SQLite 开 WAL

**验收**：空库能启动，`/healthz` 返回 200，CI 绿。

**注意**：建表时逐条对照 §5.4 的键约束表，特别是——`appeal` **刻意不加**唯一约束；`students.student_no` **允许空字符串**；`attendance` 业务唯一键是五字段复合。这三条写错，后面都要返工。

### M1 · 判定引擎与数据导入（4 人天）★ 最硬里程碑

**产出**

1. **判定纯函数**：`judge(raw_result, raw_way, leave_set) → (final_judgment, judge_reason)`，不依赖 DB 会话
2. **9 步导入管线**（01 文档 §3.1）：解析 → 日期段去重 → 学号映射 → 请假匹配 → 判定 → 500 条/批写入 → 名册补建 → 重建统计 → 写 `sync_batch`
3. **名册导入**：按列名定位、学号优先 upsert、不影响已有绑定关系与角色
4. **`class_daily_stat` 重建**：按日期段整段删旧再重算（幂等）
5. **导入层与判定引擎解耦**：接口约束「输入 11 列结构化行 → 输出判定结果」，为学校 API 预留

**验收（硬指标，不可打折）**

| 断言 | 期望 |
|---|---|
| 31,792 行判定分布 | 正常 15,442 / 旷课 14,185 / 待处理 2,001 / 迟到 164，合计 31,792 |
| 学号映射命中率 | 31,708 / 31,792 = 99.74% |
| 名册导入 | 2,418 人入库；重复导入更新而不产生重复行（场景 1） |
| 重复导入同一文件 | 全部识别为重复跳过，不产生脏数据（场景 3） |
| 10 种输入组合 | 逐组合单测，各自判定正确 |

**测试预算**：判定单测 ~23 项 + 真实数据回归 ~7 项。**真实数据回归必须进 CI 门禁**——这是防止重演 8,314 行误判的唯一保险。

**风险**：名册用错文件（R6）。导入时校验名册规模（应 ≈2,418）与年级覆盖（应含 24/25/26 级），异常则拒绝导入并明确提示。

### M2 · 登录与权限（3 人天）

**产出**

- WPS OAuth2 免密登录：`/auth/wps/login` → `/auth/wps/callback`
- 身份绑定：因 WPS 不返回学号，首次需绑定（学号 + 手机号后四位），此后长期免密；`/auth/wps/bind`、`/auth/wps/unbind`
- **兜底登录**：学号 + 手机号后四位，WPS 不可用时自动回落
- 四角色权限网关（服务端强制，01 文档 §2.5）：
  - 学生端查询强制 `student_no = 当前绑定学号`
  - 副班长/干部强制 `class_name = 本人班级`
  - 辅导员无班级约束
- 角色叠加导航（§2.2）：单值 `role` 推导双套入口
- 干部任命页 `/counselor/roles`，变更写审计日志

**验收**：场景 9 权限隔离——学生看不到他人考勤、副班长只看本班、辅导员无限制。每个端点对 4 种角色各测一遍越权。

**测试预算**：WPS 登录 ~29 项 + WPS 接口 ~52 项（含 mock）。

**注意**：`wps_user_id`（推送地址）与 `is_bound`（登录绑定）是两个不同的东西，不要在一个流程里同时写。

### M4 · 改判底座 + 待处理核对 + 手动改判（3 人天）★ 架构关键

**产出**

1. **`apply_judgment_change()` 唯一改判入口**，统一负责四件事：
   - 改 `attendance.final_judgment` + `judge_reason`
   - 增量维护 `class_daily_stat`（from -1, to +1）
   - 写 `audit_log`
   - 发 `notification`
   - 按调用方决定是否置位 `lock_judgment`
2. **禁止旁路**：代码层面约束——除本函数外，任何地方不得直接 UPDATE `final_judgment`
3. 待处理核对 `/pending`：2,001 条池，到场(正常)/缺勤(旷课) + **备注必填**，按班级分批处理
4. 辅导员手动改判 `/counselor/records/override`：改判 + 备注 + 审计 + 置锁

**验收**

- 场景 8：副班长改判 → 统计同步 → 学生收到通知 → 日志留痕
- **一致性断言测试**：随机改判 N 次后，`sum(class_daily_stat.cnt) == count(attendance)` 且分组分布完全一致
- 待处理页按班筛选可用，不一屏全渲染 2,001 条

**为什么这个里程碑排在申诉和请假之前**：用最简单的业务场景（核对只有两个选项）把最重要的架构底座建起来并测通。等到写申诉时，改判副作用已经是一个测过的黑盒。

### M5 · 申诉闭环（5 人天）

**产出**

1. **双维度状态机**：`status`（pending/approved/rejected/locked/withdrawn）× `stage`（first/second/counselor/done）
2. 学生端：`/appeals`、`/appeals/new`（佐证上传 + 理由）、`/appeals/{号}` 详情含公示倒计时
3. 审核端：`/appeals/todo` 按角色分流、`/appeals/{号}/first`、`/final`、`/withdraw`
4. **防自审**（§2.4）：副班长本人申诉 `bypass_first` 跳一审进辅导员队列；干部本人申诉不进本人待办；该班唯一干部时辅导员兜底
5. **时限规则**：一审 = 提交 + 7 天（**服务端兜底**，非仅前端禁用）；公示 = 终审 + 7 天，期满锁定
6. 超时巡检 `/counselor/appeals/sweep`：自动把超时单转辅导员
7. 申诉总览 / 代审 `/counselor/appeals`
8. 业务层保证"同一考勤同时只有一张进行中申诉单"（**不靠数据库唯一约束**）

**验收**

- 场景 6：提交 → 一审 → 二审 → 通知 → 公示倒计时 → 期满锁定
- 场景 7：副班长本人申诉跳过一审；干部本人申诉不进本人二审待办；唯一干部时辅导员能兜底
- 驳回/撤回后可补充佐证重新申诉（验证没有被唯一约束堵死）
- 超时后直接构造 POST 请求也无法通过一审（服务端兜底生效）

**测试预算**：申诉 ~38 项——这是单项测试最多的模块，因为状态机 × 防自审 × 时限三个维度交叉。

**已拍板影响（D2）**：`APPEALABLE = ("旷课", "迟到", "早退")`，早退**可**申诉。需补一条早退申诉用例（当前真实数据中早退为 0 条，用例需构造数据）。

### M6 · 请假闭环（5 人天）★ 最高风险

**产出**

1. 学生端：`/leaves`、`/leaves/new`（类型卡片 / 日期范围 / **1–12 节次可视化格子点选** / 图片上传预览 / 进度时间线）、`/leaves/{号}`
2. 公假多人：按班级/姓名搜索勾选同行学生，展示已选人数，写 `leave_student` 一行一人
3. 审批端 `/counselor/leaves`：通过 / 驳回（必填理由）/ 撤销确认；待办与历史两视图；代办公假入口
4. **四重匹配写回**：姓名 + 班级 + 日期 + 节次；`periods` 空 = 当天全部课程，`1,3,5` = 指定节次；**多单并集生效**；**只覆盖旷课**
5. **撤销语义**：`status=approved` + `revoke_requested_at` 非空 + `revoke_confirmed_at` 空 = 「撤销待确认」，**此期间请假仍然生效**；不新增枚举值
6. **回滚重判**：撤销确认后完整重判，**但必须跳过 `lock_judgment=1` 的行**
7. 副班长本班请假**只读旁观**；请假日志记录每一步

**验收**

- 场景 4：代办公假（含同行学生）→ 辅导员通过 → 相关考勤自动改判「请假」
- 场景 5：撤销已通过请假 → 辅导员确认 → 考勤回滚并重判
- **`lock_judgment` 保护专项测试**：先让副班长核对一批待处理，再通过并撤销一张覆盖同时段的请假，断言核对结论未被冲掉
- 多张公假覆盖同一学生同一时段 → 并集生效，不报错
- 正常/迟到/早退记录不被请假影响

**测试预算**：请假 ~23 项 + 工作流 ~18 项。

**风险 R2 就在这里**：路径 5 是全系统最容易出脏数据的地方。建议这个里程碑的代码单独走一次 review，重点只看一件事——"完整重判"有没有尊重人工结论锁。

---

### M7 · 通知与推送（3 人天）

**产出**

1. 站内通知 `/notifications`、`/notifications/read`——**推送失败也要落库**，学生登录后一定看得到
2. WPS IM 机器人推送，6 个场景：请假审批结果 / 撤销确认结果 / 新请假提醒（**0→1 边缘触发**，积压期不重复推）/ 申诉审核结果 / 核对结果 / 考勤日报
3. **推送铁律**：
   - 失败一律静默降级，**绝不阻塞审批主流程**
   - 未绑定 WPS 的学生跳过并计数（页面显示"未绑定跳过 N 人"）
   - 以 `students.wps_user_id` 定位接收人
   - **单组上限 100 人，超限必须分片**（超标组会整组静默丢弃且不报错）
4. 日报生成与推送 `/counselor/report`、`/counselor/report/send`：**默认取库里最新一天有数据的日期**，不是"今天"（避免周末/未导入时推空报）
5. 辅导员通知中心 + 单独重推 `/counselor/notifications/resend`
6. 定时任务：每日 21:00 北京时间，cron / systemd timer

**验收**

- 构造 150 人推送 → 断言分成 2 片且全部送达（R5）
- 模拟推送接口 500 → 审批仍然成功，通知落库且标记 `push_error`
- 日报内容格式对照 §6.3 样例
- 新请假提醒在积压期不重复推（边缘触发）

**已拍板影响（D4）**：本里程碑**只做辅导员版日报**（每日 21:00 全院汇总）。学生个人日报拆为独立需求列二期 P1，需 D6 领导点头后再开。
**D6 未决期间**：开发与测试全程走 mock 推送通道（`ATT_NOTIFY_CHANNEL=mock`），不向真实用户发送任何消息。

## 三、外部依赖：必须 Day 1 并行发起

这几项**不受开发速度控制**，但会卡上线。它们不在技术关键路径上，却在**项目**关键路径上：

| # | 依赖 | 卡住什么 | 谁来推 | 建议发起时间 | 提前期 |
