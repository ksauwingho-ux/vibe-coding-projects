**两条不可违反的依赖方向**：

## 二、数据库设计

### 2.1 通用约定

| 约定 | 说明 |
|---|---|
| **字符串列 `NOT NULL DEFAULT ''`** | 原因见下方注解 |
| 时间列 | `created_at` / `updated_at`，统一存 UTC 或统一存本地时间**二选一并写进代码注释**；推送涉及"北京时间 21:00"，建议全库存本地时间避免时区换算错误 |
| 布尔 | 用 `INTEGER 0/1`（SQLite 无原生 bool，PG 可换 `BOOLEAN`） |
| 日期 | `att_date` 用 `DATE`；`sign_time` 是原始字符串，**不解析**（原样留存以便追溯） |

> **关于"空值统一转空字符串"**：v4.0 §9.4 把这条写成硬约束，原因是旧云库不接受 null。SQLite/PG 都没有这个限制——但**建议保留这条约定**，理由变了：判定规则里到处在比较 `raw_way == ""`（空方式 → 待处理），四重匹配也在比较字符串。一旦混入 `NULL`，`NULL == ''` 在 SQL 里是 `NULL` 而非 `TRUE`，会让 2,001 条待处理静默漏判。**这是一条从平台限制升级为业务正确性要求的约定。**

**索引设计（60 万行的关键，逐条对应一个真实查询）**：

```sql
-- 我的考勤（/me）
CREATE INDEX idx_att_stu_date   ON attendance(student_no, att_date);
-- 本班考勤（/class）、看板兜底
CREATE INDEX idx_att_class_date ON attendance(class_name, att_date);
-- 待处理池（/pending）、判定管理筛选（/counselor/records）
CREATE INDEX idx_att_cls_jud_date ON attendance(class_name, final_judgment, att_date);
-- ★ 请假四重匹配专用（见下方注解）
CREATE INDEX idx_att_leave_match ON attendance(name, class_name, att_date, period);
-- 导入批次回溯
CREATE INDEX idx_att_batch ON attendance(batch_id);
```

> ⚠️ **`idx_att_leave_match` 不能省，原因不直观。**
> 业务唯一键的列序是 `(name, class_name, course_name, period, att_date)`，而请假四重匹配要按 `(name, class_name, att_date, period)` 查。`course_name` 卡在第 3 位，**四重匹配无法走唯一键索引的前缀**。没有这条专用索引，每通过一张请假单就会对 60 万行做一次全表扫；一张覆盖多人多天的公假会扫上百次。这是本系统唯一一处真正的性能陷阱。

## 三、判定引擎契约（`judge/`）

### 3.1 签名（语言无关）

```
judge(
  raw_result: str,            # 原始考勤结果
  raw_way:    str,            # 原始考勤方式（空 = ''，绝不是 null）
  covered:    bool            # 该(姓名,班级,日期,节次)是否被已通过请假覆盖
) -> (final_judgment: str, judge_reason: str, is_leave: bool)
```

**三条硬约束**：

1. **纯函数**：无 DB、无 IO、无全局状态、无当前时间依赖。同样输入永远同样输出。
2. **请假覆盖以 `covered: bool` 传入**，不在函数内查库。查询由调用方（导入管线 / 请假服务）负责构造。这是让 31,792 行回归跑在毫秒级的关键。
3. **`judge_reason` 必须非空**，且能追溯到规则条文（如 `刷卡视为不可信签到→旷课(§3.3)`）。这是 01 文档"结果可追溯"目标的唯一落地点。

### 3.2 决策表（实现时逐行对照）

| # | `raw_result` | `raw_way` | `covered` | → `final_judgment` | `is_leave` | `judge_reason` 模板 |
|---|---|---|:-:|---|:-:|---|
| 1 | 正常 | ∈ {刷脸, istudy, 二维码} | — | 正常 | 0 | `有效签到方式:{way}` |
| 2 | 正常 | 刷卡 | — | **旷课** | 0 | `刷卡可代刷,视为不可信签到` |
| 3 | 正常 | `''` | — | **待处理** | 0 | `签到方式为空,待人工核实` |
| 4 | 正常 | 其它 | — | **待处理** | 0 | `未知签到方式:{way}` ← D1 决议 |
| 5 | 迟到 | 任意 | — | 迟到 | 0 | `原始结果保留:迟到` |
| 6 | 早退 | 任意 | — | 早退 | 0 | `原始结果保留:早退` |
| 7 | 旷课 | 任意 | **true** | **请假** | **1** | `已审批请假覆盖` |
| 8 | 旷课 | 任意 | false | 旷课 | 0 | `原始结果保留:旷课` |
| 9 | 其它 | 任意 | — | **待处理** | 0 | `未识别考勤结果:{result}` |

**必须注意的三点**：

- **请假只覆盖旷课**。第 5/6 行（迟到/早退）即使 `covered=true` 也不改判——测试要专门覆盖这个组合。
- 第 2 行是全系统最容易引起学生异议的一条（9,164 行），申诉入口必须畅通。
- 第 4 行是防御性设计，实测 31,792 行不触发。**不要因为"跑不到"就省掉它**——它存在的意义是数据源变化时不静默出错。

### 3.3 回归断言（CI 门禁 #1）

断言：正常 15,442 / 旷课 14,185 / 待处理 2,001 / 迟到 164，合计 31,792

## 四、改判服务层契约（★ 全系统最重要的一个函数）

### 4.1 为什么必须收敛成一个函数

五条改判路径（申诉终审 / 待处理核对 / 手动改判 / 请假通过 / 请假撤销）都要完成同一组副作用。如果各写一遍，**统计表迟早写花，而且很难发现**——看板数字错了，没人会立刻察觉。

### 4.2 签名与契约

```
apply_judgment_change(
  session,                        # 事务会话，由调用方开启
  attendance_id: int,
  to_judgment:   str,
  reason:        str,             # 写入 judge_reason
  operator:      str,             # 审计用
  action:        str,             # audit_log.action 枚举值
  set_lock:      bool,            # 是否置位 lock_judgment
  notify:        NotifySpec|None, # None = 不通知（仅导入路径）
  respect_lock:  bool = True,     # 是否跳过已锁定的行
  is_leave:      bool|None = None # 仅请假路径传
) -> ChangeResult(changed: bool, from_judgment: str, skipped_reason: str)
```

**前置条件**

- 调用方**必须**已开启事务；本函数不自行 commit
- `to_judgment` ∈ {正常, 迟到, 早退, 请假, 旷课, 待处理}

**副作用（按顺序，全部在同一事务内）**

1. 读取当前行并加锁（`SELECT ... FOR UPDATE`；SQLite 下依赖 WAL + 写事务串行）
2. **若 `respect_lock=True` 且 `lock_judgment=1` → 直接返回 `changed=False`，`skipped_reason='人工结论锁'`，不做任何写入**
3. 若 `from_judgment == to_judgment` → 返回 `changed=False`（幂等短路，不写审计不发通知）
4. `UPDATE attendance`：`final_judgment`、`judge_reason`、`is_leave`（若传）、`lock_judgment`（若 `set_lock`）、人工留痕字段
5. `stats.delta(att_date, class_name, from_judgment, -1)` 与 `stats.delta(..., to_judgment, +1)`
6. `INSERT audit_log`
7. 若 `notify` 非空 → `notify.enqueue()`（**落库即算成功，IM 推送异步且失败不回滚**）

**返回后由调用方 commit。**

### 4.3 五条路径的调用参数表（实现时照抄）

| 路径 | `action` | `set_lock` | `respect_lock` | `notify` | 备注 |
|---|---|:-:|:-:|:-:|---|
| 申诉终审通过 | `final_approve` | **True** | False | ✓ 学生 | 终审是权威结论，可覆盖旧锁 |
| 待处理核对 | `pending_review` | **True** | False | ✓ 学生 | 备注必填，写 `pending_note` |
| 辅导员手动改判 | `override` | **True** | False | ✓ 学生 | 写 `is_overridden` / `override_by` |
| 请假审批通过 | `apply_to_attendance` | False | **True** | ✓ 申请人（汇总一条） | 逐条调用；**不覆盖人工结论** |
| 请假撤销确认 | `rollback_attendance` | False | **True** | ✓ 申请人（汇总一条） | ★ 见 4.4 |
| 导入 | — | False | — | ✗ | **不走本函数**，走批量写入 + 整段重建 |

> **`respect_lock` 的取值逻辑**：人工做出的结论（前三条）是**新的**权威判断，可以覆盖旧锁；请假的批量写回（后两条）是**规则驱动**的，不能覆盖人工判断。这个区分是 R2 风险的唯一防线。

### 4.4 请假撤销的"完整重判"该怎么做

这是全系统最容易出脏数据的地方。正确流程：

```
1. 取该请假单覆盖的全部考勤行（四重匹配，走 idx_att_leave_match）
2. 逐行：
     若 lock_judgment == 1  → 跳过，计入 skipped 计数，写审计说明"人工结论保留"
     否则 → 用 judge(raw_result, raw_way, covered=重新计算) 重判
              ↑ covered 必须重新计算：该学生该时段可能还有**另一张**有效公假
     调用 apply_judgment_change(..., respect_lock=True)
3. 汇总一条通知给申请人：「N 条恢复原判定，M 条保留人工结论」
```

**两个极易写错的点**：

- **不能直接把 `final_judgment` 改回 `旷课`**。必须重跑 `judge()`，因为该时段可能被另一张公假并集覆盖（01 文档 §3.3「多张公假并集生效」）。直接回滚成旷课会让学生凭空多出一条旷课。
- **`lock_judgment=1` 的行必须跳过**。漏掉这一条，副班长核对过的 2,001 条结论会被一次撤销静默冲掉。

### 4.5 统计维护（`stats`）

```
stats.delta(att_date, class_name, judgment, diff)   # upsert，靠唯一键 (att_date,class_name,judgment)
stats.rebuild(date_from, date_to)                   # 幂等：先按日期段 DELETE，再 GROUP BY 重算 INSERT
```

- 单条改判 → `delta(-1)` + `delta(+1)`
- 导入完成 → `rebuild(批次日期段)`
- `delta` 必须能处理"目标行不存在"（首次出现某判定）→ upsert 而非 update

**CI 门禁 #2 · 一致性断言**：

```
随机执行 N=200 次改判（覆盖五条路径）后断言：
  SUM(class_daily_stat.cnt) == COUNT(attendance)
  且 逐 (att_date, class_name, judgment) 分组计数完全相等
```

| # | 当前 `(status, stage)` | 事件 | 执行者 | 新 `(status, stage)` | 副作用 |
|---|---|---|---|---|---|
| 1 | — | 提交 | 学生 | `(pending, first)` | 设 `first_deadline = now+7d`；审计 `submit` |

| 4 | `(pending, first)` | 一审驳回 | 副班长/辅导员 | `(rejected, done)` | 驳回理由**必填**；通知学生 |
| 5 | `(pending, first)` | 超时巡检 | 系统 | `(pending, counselor)` | `now > first_deadline`；审计 `sweep_to_counselor` |

| 10 | `(pending, *)` | 撤回 | 学生本人 | `(withdrawn, done)` | 允许之后重新申诉 |

**对外展示状态**（叠加时间维度）：

| `(status, stage)` | 展示 |
|---|---|
| `(pending, first)` | 待副班长一审（剩余 N 天） |
| `(pending, second)` | 待学生干部终审 |
| `(pending, counselor)` | 待辅导员代审 |
| `(approved, done)` + `now < public_until` | **申诉成立（公示中，剩余 N 天）** ← 仅学生本人可见倒计时 |
| `(approved, done)` + `now ≥ public_until` / `(locked, done)` | **申诉成立（已锁定）** |
| `(rejected, done)` | 已驳回（可补充佐证重新申诉） |
| `(withdrawn, done)` | 已撤回 |

**防自审判定逻辑（提交时一次算清，存进 `bypass_first`）**：

```
提交人角色 == monitor 且 申诉人 == 提交人本人  → stage = counselor, bypass_first = 1
否则                                          → stage = first

二审待办查询：stage='second' AND NOT (当前用户是干部 AND appeal.name == 当前用户姓名)
  若该班干部数 == 1 且 该唯一干部就是申诉人 → 该单转 stage='counselor'（辅导员兜底）
```

> 最后一条是 R4 的技术兜底：某班只有 1 名干部是真实场景，不兜底会让该生申诉**永久卡死**。这个分支必须有测试。

### 6.2 请假（`status` + 撤销三字段）

| # | 当前状态 | 事件 | 执行者 | 新状态 | 副作用 |
|---|---|---|---|---|---|
| 1 | — | 发起 | 学生/干部代办/辅导员代办 | `pending` | 病假无佐证则拒绝；公假写 `leave_student` |
| 2 | `pending` | 通过 | **辅导员** | `approved` | ★ 四重匹配逐条 `apply_judgment_change(respect_lock=True)`；`is_applied=1`；记 `changed_records` |

| 4 | `approved` | 申请撤销 | 学生 | `approved` + `revoke_requested_at=now` | **请假仍然生效**；展示为「撤销待确认」 |

**「撤销待确认」的判定表达式**（不新增枚举值）：

```

```

**四重匹配 SQL 骨架**：

```sql
SELECT a.id, a.raw_result, a.raw_way, a.final_judgment, a.lock_judgment
FROM attendance a
JOIN leave_student ls ON ls.name = a.name AND ls.class_name = a.class_name
WHERE ls.leave_no = :leave_no
  AND a.att_date BETWEEN :start_date AND :end_date
  AND (:periods = '' OR a.period IN (:period_list))   -- '' = 按天，覆盖当天全部课程
  AND a.final_judgment = '旷课'                        -- ★ 只覆盖旷课
-- 走 idx_att_leave_match
```

## 九、通知与推送

### 9.1 两段式：落库 + 异步推送

```
业务事务内：  INSERT notification(..., pushed=0)        ← 落库即成功
事务提交后：  异步 push()  → 成功 pushed=1 / 失败 push_error=...
```

**这是"推送失败绝不阻塞审批"的技术实现**：推送不在业务事务内，失败只写 `push_error`，学生登录站内一定看得到。

### 9.2 分片（R5）

```
按 wps_user_id 分组 → 每片 ≤ 100 人 → 逐片调用 → 逐片计数
未绑定（wps_user_id == ''）→ 跳过并计入 skipped
```

> ⚠️ 超过 100 人的组会被 WPS **整组静默丢弃且不报错**，现象是"一部分人收得到、一部分人收不到"。所以分片不是优化，是正确性要求。**测试必须构造 150 人场景断言分成 2 片。**

### 9.3 推送场景（6 个，D4 决议后）

## 十、实现绑定层（受 D0 影响，待拍板后定稿）

| 关注点 | 方案 A：FastAPI + Jinja2 + SQLite（推荐） | 方案 B：React 前端 + 独立后端 |
|---|---|---|
| 数据访问 | SQLAlchemy 2.x ORM / Core | 同（后端仍需 ORM） |
| DB | SQLite + **WAL** 模式，单文件 | 同，或 PostgreSQL |
| 视图 | Jinja2 服务端渲染，24 模板 | React 组件 + 51 个 JSON API |
| 会话 | 服务端 session cookie，`HttpOnly` + `SameSite=Lax` | JWT 或 session cookie（需处理 CORS） |
| 表单 | 原生 form POST + 服务端校验 | 前端校验 + 后端**必须重复校验** |
| 文件上传 | 直接 multipart | 同 |
| 定时任务 | cron / systemd timer 调 `/counselor/report/send` 或 CLI | 同（后端侧） |
| 测试 | pytest + TestClient，页面冒烟直接断状态码 | 后端 pytest + 前端 Vitest + E2E（Playwright） |
| **额外成本** | — | **+30~40%**：51 个 API 契约、前后端两套校验、CORS/鉴权、E2E 环境；判定引擎回归若改语言需重写 |

**SQLite 下的三个必做配置**（方案 A）：

```sql
PRAGMA journal_mode = WAL;      -- 读写并发，必开
PRAGMA synchronous = NORMAL;    -- WAL 下的合理权衡
PRAGMA busy_timeout = 5000;     -- 避免并发写立即报 database is locked
```

> **SQLite 的写并发限制**：同一时刻只允许一个写事务。本系统写入场景是导入（单人操作）+ 审批（低频），2,432 人规模下不会成为瓶颈。但**批量导入必须 500 条/批分段提交**，不要开一个长事务写 31,792 行——会长时间阻塞所有读。
